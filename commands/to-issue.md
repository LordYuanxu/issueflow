把一篇草稿发布成 GitLab issue。**步骤 0**：读 `~/.agents/issueflow-config.md` 取 `<看板目录>`、`<GITLAB_HOST>`、`<gitlab_namespace>`、`<glab 路径>`（缺失则提示按 config.example.md 配置并终止）。

## 1. 定位草稿

- 参数给了笔记名/路径 → 用它（`<看板目录>` 所在 vault 内查找，先路径后文件名模糊搜索）
- 无参数 → 列出 vault 的 Inbox/日志目录最近修改的 10 篇笔记供用户选
- 用户直接口述需求 → 照常执行，仅跳过步骤 7 回链

## 2. 确定目标仓库

读 `<看板目录>/项目清单.md`，从草稿内容推断属于表中哪个仓库（本地路径以表为准）；推断不了就问用户，**不要猜**。目标仓库不在表中 → 问用户是否接入看板：是则先在登记表加一行再继续；否则按用户给的路径操作且不做回链。

## 3. 写 spec（目录遵循仓库已有约定）

整理成结构化需求文档：背景（引用草稿原话）、目标、验收标准、明确不做的边界。存放位置**仓库已有约定优先**：

- 已有设计文档目录与索引（如 `docs/design/` + README 索引）→ 写入该目录 `YYYY-MM-DD-<主题>.md` 并按格式登记索引
- 无既有约定 → `docs/specs/YYYY-MM-DD-<主题>.md`，目录不存在则创建

spec 用 git 提交并 push 到 main，提交信息沿用该仓库风格。草稿太小不足以成 spec → 跳过 spec 直接建单个 issue。

## 4. 拆解并确认（硬性卡点）

拆成 1~N 个 issue，每个给出：**标题、15-40 字摘要、标签、验收要点、建议依赖顺序**。标签两层：类型标签（feature/chore/docs/bug）必打；**审查/优化/重构类清单同时打优先级标签 P0（紧急）/ P1（常规）/ P2（低优）**，看板按标签即可排序开发。

拆解前先查重（防多会话/多助手重复建单）：执行 `glab issue list -R <仓库>`（默认即只列开放项），与拆解结果对照；意思相近的条目在表格标「⚠️ 疑似与 #N 重复」，并让用户选择跳过、并入已有 issue 或照建，未澄清前不得建该条。

以表格展示，**必须等用户明确确认才能继续**，要改就改完再确认。此步不可跳过。

## 5. 建 issue

逐条 `glab issue create --title "<标题>" --description "<摘要 + 验收要点 + spec 相对路径>" --label <标签>`（多个标签逗号分隔）。单条失败继续其余，最后统一报告失败项。

## 6. 汇报

列出新建 issue 编号与链接、spec 路径、下一步建议（按该仓库 AGENTS.md 分支纪律开工）。

## 7. 回链原笔记

原笔记 frontmatter 追加（无则新建）：`提报状态: 已提报 YYYY-MM-DD` 与 `issues:` 列表。**正文一字不动**；vault 若是 git 仓库不要自动提交。

## 典型用法

- 单个需求：`/to-issue 我的笔记名`，或直接口述
- **批量记录（审查/体验后最常用）**：`/to-issue，把这次审查的优化清单全部落成 issue，按优先级打标签，依赖顺序写进描述`——一次投喂整份清单，AI 逐条建卡、优先级入标签、依赖关系写入各卡描述。先把需求全部记录进看板，再按 P0→P2 逐个开发，避免好想法散落在笔记和对话里
